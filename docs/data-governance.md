## 1. Introduction

### 1.1 Purpose

This document establishes the data governance framework for the APEX-OS Business Platform — a multi-cloud, Kubernetes-orchestrated enterprise platform spanning AWS (EKS, RDS, S3), Azure (AKS, Storage), and GCP (GKE, Cloud Storage). The framework defines policies, standards, roles, and processes to ensure data is accurate, discoverable, protected, and managed throughout its lifecycle.

### 1.2 Objectives

| Objective | Description |
|-----------|-------------|
| **Trust** | Ensure data is accurate, consistent, and reliable for decision-making |
| **Transparency** | Provide end-to-end visibility into data origin, movement, and transformation |
| **Discoverability** | Enable self-service data discovery through a unified catalog |
| **Protection** | Safeguard sensitive and personal data in compliance with global regulations |
| **Compliance** | Meet legal, regulatory, and contractual obligations for data retention and disposal |

### 1.3 Scope

**In scope:**
- All structured, semi-structured, and unstructured data stored in platform-managed data stores (RDS PostgreSQL, S3, Azure Blob, GCP Cloud Storage, Loki logs, Tempo traces)
- Data in transit across service mesh (Istio), API gateways, and inter-cluster communication
- Metadata, configuration data, and operational data generated by platform components
- Data processed by workloads running in `apex-os-core`, `apex-os-data`, `apex-os-monitoring`, and `apex-os-security` namespaces

**Out of scope:**
- Data owned and managed by external SaaS integrations (unless explicitly contracted)
- Ephemeral in-memory data with no persistence layer
- End-user device-local data

## 2. Governance Principles

| # | Principle | Statement |
|---|-----------|-----------|
| P1 | **Accountability** | Every data asset has a designated Data Owner and Data Steward with defined responsibilities |
| P2 | **Accuracy** | Data must be correct, complete, and current; quality issues are tracked and remediated |
| P3 | **Transparency** | Data lineage is documented and accessible; transformations are explainable |
| P4 | **Discoverability** | All data assets are registered in the catalog with searchable metadata |
| P5 | **Privacy by Design** | Data protection is embedded into architecture, not bolted on |
| P6 | **Least Privilege** | Access is granted on a need-to-know basis with regular recertification |
| P7 | **Retention Discipline** | Data is retained only as long as necessary and disposed of securely |
| P8 | **Auditability** | All access and changes to governed data are logged and reviewable |

## 4. Data Quality Management

### 4.1 Quality Dimensions

| Dimension | Definition | Measurement Approach | Target |
|-----------|-----------|---------------------|--------|
| **Completeness** | All required fields are populated | Null-check ratios per table/column | ≥ 99.5% |
| **Accuracy** | Data correctly represents the real-world entity | Sampling against source systems; validation rules | ≥ 99.0% |
| **Consistency** | Data is uniform across systems and time | Cross-system reconciliation; duplicate detection | ≥ 99.5% |
| **Timeliness** | Data is available when expected | Freshness checks (last update vs. SLA) | ≥ 99.9% |
| **Validity** | Data conforms to defined formats and ranges | Schema validation; regex/range checks | ≥ 99.5% |
| **Uniqueness** | No unintended duplicates exist | Primary key / business key uniqueness scans | 100% |
| **Integrity** | Referential relationships are maintained | Foreign key validation; orphan detection | ≥ 99.9% |

### 4.2 Quality Rules Framework

#### 4.2.1 Rule Categories

| Category | Description | Example |
|----------|-------------|---------|
| **Schema Rules** | Data type, length, format constraints | `email` must match RFC 5322 pattern |
| **Business Rules** | Domain-specific logic | `order_total` = sum of `line_item` amounts |
| **Temporal Rules** | Time-based constraints | `created_at` ≤ `updated_at` ≤ `now()` |
| **Relational Rules** | Cross-table/cross-system constraints | Every `order` must reference a valid `customer_id` |
| **Statistical Rules** | Distribution-based anomaly detection | Daily transaction count within 3σ of 30-day rolling mean |

#### 4.2.2 Rule Severity Levels

| Level | Name | Action | SLA |
|-------|------|--------|-----|
| S1 | **Critical** | Block ingestion; page on-call | Immediate |
| S2 | **Major** | Quarantine record; alert steward | 4 hours |
| S3 | **Minor** | Log issue; include in daily report | 24 hours |
| S4 | **Informational** | Track in quality dashboard | Next sprint |

## 5. Data Lineage

### 5.1 Lineage Scope

Data lineage tracking covers:

| Layer | What is Tracked | Mechanism |
|-------|----------------|-----------|
| **Source Systems** | Origin databases, APIs, file drops | Source metadata registry |
| **Ingestion** | ETL/ELT pipelines, streaming connectors | OpenLineage / Marquez |
| **Transformation** | SQL transformations, aggregations, enrichments | dbt docs, Spark UI lineage |
| **Storage** | Tables, columns, partitions, objects | Automated metadata crawlers |
| **Serving** | APIs, dashboards, ML features, exports | API gateway logs, BI tool metadata |
| **Consumption** | Downstream applications, reports, models | Data catalog usage analytics |

### 5.2 Lineage Architecture

```

├──────────────┬──────────────┬──────────────┬──────────────────────┤
```

### 5.3 Lineage Metadata Model

Each lineage event captures:

| Field | Description | Example |
|-------|-------------|---------|
| `run_id` | Unique execution identifier | `run-20261001-001` |
| `job_name` | Pipeline or job name | `dbt:transactions_daily` |
| `event_type` | START / COMPLETE / FAIL | `COMPLETE` |
| `event_time` | ISO 8601 timestamp | `2026-10-01T12:00:00Z` |
| `inputs` | Source datasets (URI + schema) | `rds://prod-db/transactions/orders` |
| `outputs` | Target datasets (URI + schema) | `s3://apex-os-data-lake/curated/orders/` |
| `code_version` | Git SHA or image tag | `a1b2c3d` |
| `environment` | Deployment context | `prod` |
| `custom_facets` | Domain-specific metadata | `{"row_count": 15234, "quality_score": 99.8}` |

## 7. Data Privacy

### 7.1 Data Classification

| Level | Label | Description | Examples | Handling Requirements |
|-------|-------|-------------|----------|----------------------|
| **C1** | Public | Intended for public disclosure | Marketing content, published APIs | Standard controls |
| **C2** | Internal | For internal use only | Internal docs, non-sensitive configs | Access restricted to employees |
| **C3** | Confidential | Business-sensitive, limited distribution | Customer PII, financial records, contracts | Encryption, access logging, DLP |
| **C4** | Restricted | Highly sensitive, need-to-know basis | Credentials, health data, SSNs, payment data | Encryption, tokenization, strict ACLs, DLP, approval workflow |

### 7.2 PII and Sensitive Data Inventory

| Data Element | Classification | Storage Locations | Encryption | Tokenization |
|--------------|---------------|-------------------|------------|--------------|
| Email address | C3 | RDS `crm.customers`, S3 exports | AES-256 at rest, TLS 1.3 in transit | No |
| Phone number | C3 | RDS `crm.customers` | AES-256 at rest, TLS 1.3 in transit | No |
| Full name | C3 | RDS `crm.customers`, `identity.users` | AES-256 at rest, TLS 1.3 in transit | No |
| Government ID (SSN, passport) | C4 | RDS `identity.verification` (isolated schema) | AES-256 at rest, TLS 1.3 in transit | Yes (format-preserving) |
| Payment card data | C4 | External processor (Stripe/Adyen); never stored in platform | N/A (tokenized by processor) | Processor tokenized |
| Health information | C4 | RDS `health.records` (if applicable) | AES-256 at rest, TLS 1.3 in transit | Yes |
| API keys / secrets | C4 | Kubernetes Secrets (external secrets operator) | AES-256 at rest, TLS 1.3 in transit | N/A |
| Authentication tokens | C4 | RDS `identity.sessions`, Redis cache | AES-256 at rest, TLS 1.3 in transit | Hashed (bcrypt/argon2) |

### 7.3 Privacy by Design Principles

| Principle | Implementation |
|-----------|---------------|
| **Proactive not Reactive** | Privacy impact assessments (PIA) required before new data collection |
| **Privacy as Default** | Maximum privacy settings applied automatically; data minimization enforced |
| **Privacy Embedded into Design** | Data classification tags enforced at schema level; DLP policies in CI/CD |
| **Full Functionality** | Privacy controls do not degrade core platform capabilities |
| **End-to-End Security** | Encryption at rest, in transit, and in use (confidential computing where feasible) |
| **Visibility & Transparency** | Public privacy policy; internal data processing register |
| **Respect for User Rights** | Self-service data export and deletion workflows |

### 7.4 Data Subject Rights (DSR) Support

| Right | Description | Platform Capability |
|-------|-------------|-------------------|
| **Access** | Provide copy of all personal data | Self-service export API; 30-day SLA |
| **Rectification** | Correct inaccurate personal data | Admin API + audit trail |
| **Erasure (Right to be Forgotten)** | Delete all personal data | Automated deletion workflow with verification |
| **Restriction** | Limit processing of personal data | Processing flags in identity service |
| **Portability** | Provide data in machine-readable format | JSON/CSV export via API |
| **Objection** | Opt out of specific processing | Consent management system |

### 7.5 Privacy-Enhancing Technologies (PETs)

| Technology | Use Case | Implementation |
|------------|----------|---------------|
| **Tokenization** | Replace PII with non-sensitive tokens | Format-preserving tokenization service for C4 data |
| **Differential Privacy** | Analytics on aggregated data without individual exposure | Noise injection in reporting queries |
| **K-Anonymity** | Data masking for analytics datasets | Generalization of quasi-identifiers |
| **Homomorphic Encryption** | Computation on encrypted data | Evaluated for specific C4 analytics use cases |
| **Secure Enclaves** | In-use protection for sensitive processing | AWS Nitro Enclaves / Azure Confidential Computing |

### 7.6 Cross-Border Data Transfer

| Scenario | Mechanism | Legal Basis |
|----------|-----------|-------------|
| EU → US | EU-US Data Privacy Framework + Standard Contractual Clauses (SCCs) | Adequacy decision + SCCs |
| EU → Other | SCCs + Transfer Impact Assessment (TIA) | Chapter V GDPR |
| Intra-platform (multi-cloud) | Binding Corporate Rules (BCRs) where applicable | Article 47 GDPR |

### 7.7 Privacy Monitoring and Breach Response

| Activity | Frequency | Responsible |
|----------|-----------|-------------|
| DLP policy review | Monthly | Security Team |
| Access log review (C3/C4 data) | Weekly | Data Stewards |
| PII scan (automated) | Daily | DLP Engine |
| Penetration testing (data exfiltration) | Quarterly | External auditors |
| Privacy impact assessment | Per new feature/project | DGC |

**Breach Response Timeline:**

| Phase | Timeframe | Action |
|-------|-----------|--------|
| Detection | T+0 | Automated DLP alert or manual report |
| Containment | T+1 hour | Isolate affected systems; revoke compromised access |
| Assessment | T+24 hours | Determine scope, data types, and affected individuals |
| Notification | T+72 hours | Report to supervisory authority (GDPR Article 33) |
| Remediation | T+7 days | Root cause fix; additional controls |
| Individual notification | T+14 days | Notify affected data subjects if high risk |
| Post-incident review | T+30 days | Lessons learned; policy updates |

## 8. Data Retention

### 8.1 Retention Policy Framework

Retention periods are determined by:

1. **Legal/Regulatory Requirements** — statutory minimum retention periods
2. **Business Requirements** — operational and analytical needs
3. **Contractual Obligations** — customer and partner agreements
4. **Risk Considerations** — litigation hold and audit requirements

### 8.2 Retention Schedule by Data Category

| Data Category | Data Examples | Retention Period | Disposal Method | Legal Basis |
|---------------|---------------|-----------------|-----------------|-------------|
| **Financial Transactions** | Orders, invoices, payments, refunds | 7 years | Crypto-shredding + deletion | Tax codes, SOX |
| **Customer Account Data** | Profiles, preferences, consent records | Account lifetime + 2 years | Crypto-shredding + deletion | GDPR, CCPA |
| **Authentication & Access** | Login history, session tokens, MFA events | 1 year | Secure deletion | Security policy |
| **Security Audit Logs** | CloudTrail, GuardDuty, VPC Flow, Azure Activity, GCP Audit | 3 years | Secure deletion | SOC 2, ISO 27001 |

### 8.3 Retention Implementation by Storage System

#### 8.3.1 RDS PostgreSQL

| Mechanism | Configuration |
|-----------|--------------|
| **Table partitioning** | Monthly partitions for time-series tables (transactions, events) |
| **Partition dropping** | Automated `DROP PARTITION` after retention period expires |
| **pg_cron jobs** | Daily cleanup of expired rows in non-partitioned tables |
| **RDS snapshots** | Automated daily snapshots with 35-day retention; monthly snapshots archived to S3 with 12-month retention |
| **Point-in-time recovery** | 35-day backup window |

```sql
-- Example: Automated partition cleanup
CREATE OR REPLACE FUNCTION drop_old_partitions()
RETURNS void AS $$
DECLARE
    partition_name TEXT;
    cutoff_date DATE := CURRENT_DATE - INTERVAL '7 years';
BEGIN
    FOR partition_name IN
        SELECT tablename FROM pg_tables
        WHERE tablename LIKE 'orders_20%'
          AND tablename < 'orders_' || to_char(cutoff_date, 'YYYY_MM')
    LOOP
        EXECUTE format('DROP TABLE IF EXISTS %I', partition_name);
        RAISE NOTICE 'Dropped partition: %', partition_name;
    END LOOP;
END;
$$ LANGUAGE plpgsql;
```

### 8.4 Legal Hold

| Aspect | Process |
|--------|---------|
| **Trigger** | Legal counsel issues written hold notice |
| **Scope** | Specific data assets, systems, or time ranges identified |
| **Effect** | Suspends all automated deletion for in-scope data |
| **Duration** | Until hold is formally released by legal counsel |
| **Audit** | All holds logged with issuer, date, scope, and release date |
| **Review** | Quarterly review of active holds with legal team |

### 8.5 Disposal Methods

| Method | Use Case | Verification |
|--------|----------|-------------|
| **Crypto-shredding** | Encrypted data where deletion of encryption key renders data inaccessible | Key destruction certificate |
| **Secure overwrite** | Storage media decommissioning | NIST 800-88 Rev. 1 Clear/Purge |
| **Physical destruction** | End-of-life hardware | Certificate of destruction |
| **Logical deletion** | Row-level removal with verification | Post-deletion scan confirmation |
| **Anonymization** | Data retained for analytics with PII irreversibly removed | Re-identification risk assessment |

### 8.6 Retention Compliance Monitoring

| Check | Frequency | Responsible | Action on Violation |
|-------|-----------|-------------|---------------------|
| Orphaned data scan (data without registered retention policy) | Monthly | Data Custodians | Register or delete within 14 days |
| Expired data scan (data past retention period) | Weekly | Automated | Alert + auto-delete if no legal hold |
| Legal hold compliance | Per hold | Legal + Data Owners | Verify no deletion occurred |
| Disposal verification | Per disposal | Data Custodians | Certificate filed; audit log updated |
| Retention policy review | Annually | DGC | Update policies for regulatory changes |

## 9. Cross-Cutting Concerns

### 9.1 Access Control

| Layer | Mechanism | Policy |
|-------|-----------|--------|
| **Network** | Security groups, NSGs, firewall rules, Istio mTLS | Zero-trust; deny by default |
| **Authentication** | OIDC (Azure AD / AWS IAM / GCP IAM) | MFA required for all human access |
| **Authorization** | RBAC (Kubernetes IAM, AWS IAM, Azure RBAC, GCP IAM) | Least privilege; just-in-time elevation |
| **Data Access** | Row-level security, column-level encryption, dynamic data masking | C3/C4 data masked by default for non-privileged roles |
| **Audit** | CloudTrail, Azure Activity Log, GCP Audit Logs, database audit logs | All access to C3/C4 data logged |

### 9.2 Encryption

| State | Standard | Key Management |
|-------|----------|---------------|
| **At Rest** | AES-256 (RDS, S3, Azure Blob, GCS, EBS, etcd) | AWS KMS / Azure Key Vault / GCP Cloud KMS with automatic rotation (90 days) |
| **In Transit** | TLS 1.3 (minimum TLS 1.2) | cert-manager with Let's Encrypt / ACM; Istio mTLS for service-to-service |
| **In Use** | Confidential computing (AWS Nitro, Azure Confidential VMs) | Evaluated for C4 data processing |
